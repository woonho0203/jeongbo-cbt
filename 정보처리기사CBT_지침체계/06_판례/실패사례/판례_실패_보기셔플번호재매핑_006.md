# 판례_실패_보기셔플번호재매핑_006

## 사건명

해설 재작성 2차분(258건) 검수 중 앱 렌더링을 실제로 확인하다가, **앱이 보기를 무작위로 섞는데 해설 속 보기 번호를 제대로 재매핑하지 못해 학습자에게 틀린 번호가 표시되는** 결함을 발견한 사례. 데이터가 아니라 앱 코드(`public/js/util.js`의 `remapExplanationNumbers`)의 정규식이 근본 원인이며, 지침에 "셔플 안전 표기 규칙"이 없어 방치됐다.

## 결과

앱은 `public/js/exam.js`에서 매 세션 보기를 무작위로 섞고(`shuffleMap`), `remapExplanationNumbers(text, shuffleMap)`로 해설 속 번호를 화면 순서에 맞게 바꾼다. 그런데 인식 정규식이 `/[①②③④⑤]|([1-4])번/`뿐이라 두 방향으로 오작동한다.

**(A) 미변환 — 376문항**: 나열형 표기에서 마지막 항목에만 `번`이 붙어 앞 숫자들이 변환되지 않는다. 보기가 역순으로 섞인 경우 실측:

```text
원문: 삼각형으로 연결해 틀렸으며 실제 표기는 마름모다. 1·2·4번은 올바른 표기다.
화면: 삼각형으로 연결해 틀렸으며 실제 표기는 마름모다. 1·2·1번은 올바른 표기다.   ← 1 중복, 4 소실

원문: 폭포수 모델의 개발 방식으로 XP의 원리가 아니다. 2·3·4번은 모두 XP 기본 원리다.
화면: 폭포수 모델의 개발 방식으로 XP의 원리가 아니다. 2·3·1번은 모두 XP 기본 원리다.
```

분포: exam_2022-1(34)·2022-2(34)·2021-3(30)·2024-2(28)·2024-3(26)·2025-1(26)·2025-2(26)·2025-3(24)·2021-2(23)·2022-3(23)·2023-1(23)·2023-2(22)·2023-3(21)·2021-1(16)·2024-1(11)·category_sequence(7)·2016-1(1)·2016-3(1) = **376문항**.

**(B) 오변환 — 6문항**: 보기 번호가 아닌 숫자에 `번`이 붙어 있으면 보기 번호로 오인해 값을 바꾼다. 실측(exam_2016-1 Q25):

```text
원문: 비트 세트(Set)는 OR 연산을 사용함. 0번, 2번, 4번째 비트를 1로 세트하려면…
화면: 비트 세트(Set)는 OR 연산을 사용함. 0번, 3번, 1번째 비트를 1로 세트하려면…   ← 비트 위치가 변조됨
```

## 실패 이유

1. **탐지 사각지대**: 자동 점검(고시 제1~4조)은 JSON 정합성·템플릿·이미지 경로만 본다. "앱이 렌더링한 최종 화면"을 검사하는 항목이 없어, 데이터가 아무리 정확해도 표시 단계에서 왜곡되는 것을 잡지 못했다. 데이터관리법 제3조 4호가 요구하는 "앱 실행 확인"이 지금까지 육안 확인 수준에 머물러 이 결함을 지나쳤다.
2. **지침 공백**: 앱이 보기 셔플을 도입했으면 고시_해설_해설형식에 "셔플 안전 표기 규칙"(번호는 항상 `N번` 단위로 각각 표기, 보기 번호가 아닌 숫자에 `번`을 붙이지 않음)이 있어야 하는데 없다. 해설작성법·고시 어디에도 보기 번호 표기 규약이 없어 작성자마다 `1·2·4번`, `1, 2, 4번`, `①②④` 등 제각각 썼다.
3. 범위가 특정 시기에 몰리지 않고 2016~2025 거의 전 회차에 퍼져 있어, 특정 생성기의 문제가 아니라 **표기 규약 부재**가 원인임이 드러난다.

## 적용 기준 (교훈 한 문장)

데이터가 정확한 것과 화면에 정확히 보이는 것은 다르다. 표시 단계에서 데이터를 가공하는 로직(셔플·재매핑·치환)이 있으면, 검수는 원본 JSON이 아니라 **그 로직을 통과한 최종 출력**을 대상으로 해야 한다.
